1. What data this app collects

A visitor submits two things: a dollar amount and a 5-digit US zip code. The zip code is converted to a US state in memory and is never written to storage. What persists is:

  • State — a two-letter code such as CA
  • Amount — a number between $0.01 and $100.00
  • Timestamp — set by the server, not the browser

The application's own database does not contain names, email addresses, phone numbers, postal addresses, zip codes, account identifiers, IP addresses, or any identifier that links two submissions to the same person. There are no user accounts and no login. Two submissions from the same household are indistinguishable from two different households.

The page uses a basic analytics script to count visits and see how people move through it. It is optional: with no analytics key configured, no analytics script loads at all. Analytics is kept separate from the submitted amounts and shares no identifier with them.

On HIPAA specifically: this application does not process, store, or transmit protected health information. The HIPAA Security Rule references in the mapping table show which safeguard families the underlying technical controls belong to.

4. Access control and identity

  • Two separate machine identities, each purpose-built. The build identity can read the source bucket, write logs, and push an image. The runtime identity can read that image and use the database. Neither can do the other's job.
  • The runtime identity holds exactly one project-level role (roles/datastore.user) — database read/write, and nothing else. It cannot create infrastructure, read other buckets, or manage IAM.
  • No default or shared service account is used, and no broad owner/editor/viewer role is granted anywhere in this deployment.
  • No credentials in configuration. The container receives only two environment variables — the Google Cloud project ID and the database name. Authentication uses Google's workload identity; there is no API key, password, or connection string to leak.
  • The web page itself is intentionally public — see section 6.

5. Encryption, availability and integrity

  • In transit: the site is served over HTTPS only, with a Google-managed certificate and TLS terminated by Google's front end. Plain HTTP is redirected.
  • At rest: encrypted with Google-managed AES-256 keys, the platform default. Customer-managed encryption keys (CMEK) are not configured.
  • Point-in-time recovery is enabled on the database, so it can be restored to an earlier moment.
  • Delete protection is enabled on the database — it cannot be deleted by an ordinary API call or an accidental teardown.
  • The service is capacity-bounded to a maximum of 3 instances, which caps both cost and the blast radius of a traffic flood.
  • Submitted values are validated and bounded server-side: amounts must fall between $0.01 and $100.00, and non-numeric, infinite, and out-of-range values are rejected. A single visitor cannot meaningfully distort the published average.
  • Output is escaped. Nothing a visitor types is ever rendered as markup — server-side templating escapes by default and the browser code assigns text, never HTML.

6. Known gaps

  • The service is deliberately open to the internet. Anyone can load the page and submit a value — that is the point of a public campaign. The scanner has no check for this (it isn't a policy category it covers); being public was confirmed by direct inspection.
  • No rate limiting or bot protection. Submissions are unauthenticated and unthrottled. Amounts are bounded to $0.01–$100.00 per submission, so a script can inflate the submission count but not push a single value out of range, though it could still skew the published average.
  • No automated retention or deletion schedule on submitted records. They are retained until deleted by hand. Because the records are anonymous by construction, there is no subject to a deletion request.
  • The database has no automated policy coverage at all (section 2).
  • This is a development environment. It has not been through a production promotion, which is where change approval gating would normally apply.
  • No independent penetration test or vulnerability scan has been performed against this application.
  • Container base image patching is not automated. The image is rebuilt only when the app is redeployed, so a base-image vulnerability disclosed after the last deploy would remain until the next one.

7. Change management and audit trail

  • Every deployment is recorded with a unique identifier, the exact version deployed, who triggered it, and a timestamp. The two identifiers in the scope table above are that record.
  • All infrastructure is declared as code and versioned; nothing here was configured by hand in a console.
  • Each build produces an immutably tagged image, tagged with the deployment timestamp. The deploy stage verifies that exact tag exists in the registry before releasing it, so a deployment cannot silently ship a stale or different image.
  • Infrastructure provider plugins are cryptographically signature-verified at deploy time (signing keys 0C0AF313E5FD9F80 and 6758F1FC1D4FE114).
  • The policy scan shown on this page runs on every deployment, not on request.
